# Catalyst profiling: September 25, 2026

## Scope

Profiled the actual installed OpenClient 1.0.21 (40) Catalyst Debug app on macOS
26.2, built with Xcode 26.1. The original process, PID 10906, had been running
since September 23 at 11:38. No restart occurred before the initial captures.
The installed debug dylib matched the existing local build by SHA-256 before
changes were made.

Collected a ten-second `sample`, a sixty-second Instruments Time Profiler trace,
and two memory graphs approximately nine minutes apart. Memory graphs and leak
reports used `--noContent` to avoid including allocation contents. Raw artifacts
remain outside the repository under `/tmp/openclient-10906-20260925-*`.

## Findings

- Initial `vmmap` footprint: 636.9 MiB; historical peak: 933.7 MiB.
- Memory-graph footprints: 647.9 MiB at 10:41 and 631.1 MiB at 10:50. This short
  interval did not show monotonically increasing memory.
- The leak detector reported 288,512 unreachable bytes, mostly beneath
  `SFSpeechRecognizer`, plus a small UIKit menu cycle. This does not rule out
  unnecessary retention of reachable data, but does not explain hundreds of
  megabytes as a conventional unreachable-object leak.
- Both graphs contained one AppViewModel, one event manager, one managed-event
  batcher, one Activity facade, one SessionList facade, and 29 directory stores.
- The first graph contained two managed-event backing arrays of 29,999,104 bytes
  each: one referenced by the batcher queue and another by a delivery task. The
  later graph retained one such array. The queue retained high-water capacity;
  extracting an array from its prefix could also retain large backing storage
  during delivery. These observations are not a measurement of pending count.
- The CPU trace contained 27.699 seconds of main-thread sampled CPU weight.
  SessionList snapshot refresh tasks accounted for about 25.9%, Activity refresh
  about 13.8%, and the union of SwiftUI rendering/AttributeGraph updates about
  42.7%. These categories are disjoint. Framework menu work outside the rendering
  category accounted for another 8.3%.
- SessionList repeatedly normalized unchanged message text and materialized
  entire transcripts. Activity repeatedly scanned directory/session collections
  to find each row's owner. Both costs were directly present in sampled stacks.
- No potential-hang records appeared in this trace; that is not proof of no jank.

## Changes

- Managed-event delivery now copies at most 24 events into fresh batch storage
  and releases queue capacity when it empties, before awaiting callbacks.
  Event ordering, coalescing, and stop semantics remain unchanged. This does not
  introduce dropping or backpressure, or solve all large-backlog costs.
- SessionList caches normalized previews and unchanged form-tree results, prunes
  presentation caches, reads relevant message/part entries directly, and
  coalesces snapshot refreshes for 50 ms instead of merely yielding.
- SessionList's general preview fallback materializes only the relevant envelope
  while preserving existing text/date and wrong-session filtering semantics.
- Activity and SessionList build one ephemeral session-owner lookup per snapshot,
  preserving the single-lookup method's active-store and fallback precedence.

## Validation

262 tests passed on each of iPhone 17 Pro Max and iPad Pro 13-inch (M5), iOS 26.1,
with normal simulator signing. Coverage includes queue-capacity release during
suspended delivery, reentrant event ordering, stop/coalescing behavior, owner
precedence, cached-preview invalidation, and existing streaming/Activity tests.
Catalyst build, code-signature verification, and localization lint passed.

In the warmed SessionList benchmark, thirty snapshots of the synthetic
long-transcript fixture took about 4.18-4.61 ms per iteration on the iPhone
simulator. This is not a whole-app responsiveness measurement or a comparison
with the original implementation.

## Fresh-process follow-up

Installed the patched build and recorded PID 42819, launched at 11:11. The
follow-up memory graph at 11:13 showed 369.2 MiB footprint, 620.4 MiB peak, and no
managed-event backing-array allocation. The same 29 directory stores and single
app/event/facade owners remained. The leak detector reported 3,312 bytes.

The follow-up trace had 5.301 seconds of main-thread sampled CPU weight. Selected
inclusive paths are below; rows overlap and must not be summed.

| Path | Aged process | Fresh patched process |
| --- | ---: | ---: |
| SessionList.makeSnapshot | 7.152 s | 0.053 s |
| SessionList.activityLatestText | 4.098 s | 0.022 s |
| Activity.refreshSnapshot | 3.816 s | 0.184 s |
| DirectoryStoreRegistry.ownerStore | 2.012 s | 0.021 s |
| DirectoryStoreRegistry.sessionOwnerSnapshot | Not present | 0.006 s |
| SwiftUI render/AttributeGraph union | 11.817 s | 3.049 s |

These are CPU sample weights, not invocation counts or elapsed function timings.
The process age, cached history, interaction sequence, and incoming event rate
were not matched. The follow-up therefore supports checking the targeted paths,
but cannot establish an overall percentage improvement or prove the long-running
regression fixed. Debug-build results also do not establish Release performance.

Follow-up artifacts are under `/tmp/openclient-42819-20260925-*`. Raw traces may
contain process metadata and local paths; review them before sharing. Temporary
files can be removed by the OS and are deliberately not committed.

## Remaining checks

- Repeat a long-running multi-session workload and compare retained memory and
  responsiveness after hours of use, not just after restart.
- Investigate remaining SwiftUI/layout and Catalyst menu invalidation with a
  controlled interaction sequence if slowdown persists.
- Consider bounded session-cache policies and amortized queue draining only with
  further measurements; no canonical session data was evicted in this change.

## Subsequent OpenCode 2 integration

When rebasing this local work onto main `84e0cb6`, the new
`ownerStoresBySessionID()` implementation replaced the local
`sessionOwnerSnapshot()` helper, including main's updated ownership precedence.
Main's 200 ms transcript-only throttle and prompt metadata refreshes were kept
instead of the earlier general 50 ms coalescing change. The bounded preview/form
caches and event-queue storage fix remain layered on top. Canonical row previews
also cache their single source envelope, preserving main's preference for live
transcript data without repeating normalization for unchanged text.

The measurements above describe the September 25 builds, not the combined
OpenCode 2 build; they are retained as historical profiling evidence.
