# V2 Catalyst lag investigation — September 29, 2026

Profiled the installed Catalyst Debug process (PID 77658), on top of `ef55adb`,
while connected to V2. Captured a 10-second `sample` and a 30-second Time Profiler
trace before changing or restarting the app.

## Measured costs

The trace contains 30.044 seconds of main-thread Running sample weight across a
30.484-second sample timestamp span: the UI thread was nearly saturated.
Inclusive weights below overlap and must not be summed.

| Path | Main-thread sample weight |
| --- | ---: |
| SwiftUI render / AttributeGraph update union | 21.449 s |
| Activity snapshot refresh | 2.071 s |
| V2 event handler | 1.632 s |
| Order-preserving transcript replacement | 1.272 s |
| Local chat-cache writes | 1.239 s |
| V2 session/timeline reconciliation | 0.437 s |

This establishes client-side CPU pressure, not a V1/V2 server latency comparison.
No matched V1 workload was captured in this investigation.

## V2 differences found in code

- `handleV2Event` synchronously projects events and applies whole transcript
  snapshots. Even events without a transcript projection run the recovery-cleanup
  replacement path. It also publishes a root view-model change for each session
  event. V1 has an existing transcript-event buffering path.
- `replaceMessagesPreservingOrder` deduplicated the incoming page, then rebuilt
  its message array with repeated linear searches and copy-on-write append
  operations. It removed and rebuilt all parts before checking state equality.
- V2 reconnect hydration schedules reconciliation for discovered sessions;
  reconciliation fetches session metadata, interactions, and a 200-message page,
  bridging older loaded pages where necessary. These requests can generate
  substantial decode, persistence, and presentation work.
- V2 disk-cache writes decoded the existing transcript for merging, decoded it
  again for equality, and encoded the new transcript before checking equality.

## Targeted changes

- Build the canonical-order message array once. Preserve first-ID position,
  last-ID content, part filtering/order, removals, and session isolation.
- Update only changed message/part entries. Return whether the session transcript
  changed so `DirectoryStore` can avoid rebuilding and comparing unrelated state.
- Fetch/decode the disk-cache record once, reject stale writes before decoding,
  and encode only changed content. Preserve page merging, tombstones, and write
  timestamps, including the newer-unchanged-write guard against older data.

## Controlled benchmark

The tests retain the original replacement implementation as a semantic oracle and
benchmark baseline. Five repeated unchanged replacements of the same 1,000-message
fixture, ten XCTest measurements on iPhone 17 Pro Max / iOS 26.1 simulator:

- Original: **598.789 ms mean**
- Updated: **15.167 ms mean**

This is roughly **39× faster for that operation**, not a whole-app speedup.

On iPad Pro 13-inch (M5), iOS 26.1, the same benchmark measured 602.855 ms
original versus 15.655 ms updated (about 38.5×).

## Remaining work

SwiftUI rendering is the largest measured cost. V2 still lacks V1's transcript
presentation buffering and performs broad reconciliation. Those require a separate
event/publication scheduling change with ordering, terminal-event, recovery,
multiwindow, and reconnect coverage. The narrow changes above do not claim to
resolve all V2 lag or change the server's canonical reconciliation semantics.

Raw captures and test results are outside the repository in the approved temporary
`opencode` directory, prefixed `v2-lag-`. They may be removed by the OS.

## Follow-up: chat selection

After the first fixes, device feedback confirmed improvement but reported slow
chat selection. A further 30-second trace of PID 95607 (`v2-selection-before`)
still showed heavy main-thread presentation work. It does not isolate per-click
wall-clock latency or establish a before/after selection speedup.

Inspection identified additional selection-path costs, addressed separately:

- Explicit V2 session selection awaited the global status response before starting
  transcript hydration. These now run concurrently, retaining navigation and
  lifecycle guards. A gated-network regression verifies that the transcript is
  presented while the status response is still suspended.
- V2 initial hydration always requested 200 records. Cold chats now start with 20;
  warm chats request their cached window size, bounded to 20–200. The existing
  history cursor remains available for older pages. A coordinator follows pages
  containing only non-displayable records until it finds messages or reaches the
  end, with cancellation and repeated-cursor checks.
- Activity selection reset directory, MCP, and files state even between chats in
  the same V2 workspace. That path now performs only the session handoff when
  directory and workspace identity match. Cross-workspace resets remain covered.
  The selected session's cached interactions are applied synchronously so keeping
  workspace state does not carry the previous chat's todos or prompts forward.

These changes reduce required work and network dependencies on chat opening.
They do not establish that SwiftUI's remaining rendering load has been eliminated.

Follow-up validation: 152 tests passed on each of iPhone 17 Pro Max and iPad Pro
13-inch (M5), iOS 26.1, including foreground/preload races, status blocking,
pagination, scope changes, interactions, and multiwindow coverage. Catalyst build
and signature verification passed; the updated app was installed and launched as

## Follow-up: lag with incoming events stopped, including typing

User feedback showed that selection and typing remained slow even while the
browser's event feed was quiet. PID 9594 used about 103% CPU after seven minutes
of uptime. The new sample (`ui-idle-typing.sample.txt`) still contained repeated
`reconcileV2KnownSession`, transcript HTTP decoding, persistence, and Activity
refresh work. This is app-generated work, not evidence of an SSE flood.

The reconnect path had two amplification points:

1. `requestV2Reconciliation(reconnect: true)` queued every listed session and
   every cached transcript, including closed idle history.
2. Directory hydration queued every discovered session again after the original
   queue had already been drained into a local batch. This caused a second pass.

Each queued session performs session-info, permission, form, and transcript
reads. With a large history, a single connection can keep producing network,
cache, and UI work for a long time without any new business events.

The follow-up change limits automatic reconnect transcript recovery to the
selected chat, other open windows, running sessions, and pending interactions.
Directory-wide permission/form inventories discover attention-needed sessions
without fetching every idle transcript. Opening an idle chat still performs its
normal canonical hydration. Bootstrap-discovered work is deduplicated into the
current pass and the selected chat is processed first. Generation/cancellation
checks prevent an obsolete reconnect task from draining a newer task's queue.

Tests cover a thousand idle cached sessions producing no automatic transcript
work, open-window interest, running and newly blocked sessions, clearing a
previously pending request, and exactly one transcript read per relevant session.

Validation: 189 tests passed on each required iPhone/iPad simulator on iOS 26.1.
Catalyst build and signature verification passed; installed process PID 15151
retained established connections to the local server. At 81 seconds of uptime it
had used 10.11 seconds of total process CPU, compared with the previous process
still using about 103% CPU after 21 minutes. The first post-install 60-second
Time Profiler capture contained 76 ms of main-thread Running sample weight and no
sampled reconciliation/cache-write frames. This observational capture is not a
matched workload benchmark. A second interaction capture was also started.

The completed 60-second interaction capture contained 25.011 s main-thread
sample weight, including 14.231 s in rendering/graph updates, 2.044 s in cache
writes, and 0.232 s in reconciliation (inclusive categories overlap). Interaction
work is still substantial, but this is distinct from continuous idle backfill;
the user's input sequence was not controlled or timed as a latency benchmark.

User verification after this installation: **switching chats was definitely
smoother and typing felt much better**. This supports the automatic background
backfill diagnosis more directly than the earlier per-operation microbenchmarks.
